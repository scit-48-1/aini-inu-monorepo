# 프로젝트 도메인 분류 기준 정리

## 문서 목적

이 문서는 현재 프로젝트가 왜 최상위 구조를 약 10개의 도메인/컨텍스트로 나누고 있는지 설명하기 위한 정리 문서다.

핵심 질문은 다음과 같다.

- 이 프로젝트에서 "도메인"은 무엇을 기준으로 나뉘는가?
- 왜 어떤 것은 핵심 도메인이고, 어떤 것은 보조 컨텍스트인가?
- `walk`와 `community`, `notification`과 `common`처럼 헷갈리기 쉬운 경계는 어떻게 구분해야 하는가?

이 문서는 참조 목록보다는 실제 구조를 읽었을 때 드러나는 설계 의도를 이해하기 쉽게 풀어쓴다.

---

## 한 줄 결론

이 프로젝트의 도메인 분리는 "기술 레이어" 기준이 아니라 "업무 책임과 상태 변화의 경계" 기준이다.

즉, 컨트롤러끼리 모으거나 서비스끼리 모으는 방식이 아니라, 먼저 "어떤 업무를 하나의 책임 단위로 볼 것인가"를 정하고, 그 안에 `controller`, `service`, `repository`, `entity`, `dto`를 넣는 구조다.

쉽게 말하면 다음 질문에 대한 답이 도메인 경계를 만든다.

- 이 데이터는 누가 소유하는가?
- 이 기능의 상태 변화는 어디서 책임지는가?
- 권한 규칙과 예외 코드는 어느 업무 규칙에 속하는가?
- 다른 기능이 이 데이터를 소비하더라도, 원천 규칙은 어디에 있는가?

---

## 이 프로젝트에서 도메인을 나누는 실제 기준

### 1. 원천 데이터와 규칙의 소유권

가장 중요한 기준은 "누가 원천 규칙을 소유하느냐"다.

예를 들어:

- 회원 가입, 프로필, 팔로우, 인증은 `member`
- 반려견 등록, 품종, 성향, 산책 스타일은 `pet`
- 산책 모집글, 참여 신청, 산책 일기, 산책 세션은 `walk`

여기서 핵심은 어떤 화면에서 쓰이는지가 아니라, 데이터와 규칙의 원래 주인이 누구냐는 점이다.

예를 들어 산책 일기가 피드나 스토리 화면에 노출되더라도, 일기의 생성 규칙과 연결 규칙은 여전히 `walk`가 소유한다.

### 2. 상태 변화의 생명주기

도메인은 "상태가 어떻게 변하는가"를 기준으로도 분리된다.

예를 들어 `walk`는 단순히 산책 관련 화면을 모아둔 것이 아니라, 다음 생명주기를 가진 업무 묶음이다.

- 모집글 생성
- 신청
- 승인 또는 거절
- 채팅 연결
- 실제 산책 진행
- 산책 일기 작성

이 흐름은 하나의 연속적인 업무 사이클이므로 `walk` 안에 묶여 있는 것이 자연스럽다.

반대로 `chat`은 대화방 생성 후 메시지 송수신, 읽음 처리, 리뷰, 산책 확인 같은 별도의 상호작용 생명주기를 가진다. 그래서 `walk`에서 파생될 수는 있어도 같은 도메인으로 흡수되지는 않는다.

### 3. 권한 규칙과 예외 코드의 묶음

도메인이 분리되면 에러 코드와 권한 규칙도 같이 분리된다.

현재 구조에서도 회원, 반려견, 산책, 채팅, 커뮤니티, 실종 관련 예외가 도메인별로 따로 관리된다. 이것은 단순 네이밍 취향이 아니라, 업무 규칙이 서로 독립적이라는 신호다.

예를 들어:

- 내 반려견만 수정할 수 있는 규칙은 `pet`
- 내 모집글만 수정할 수 있는 규칙은 `walk`
- 채팅방 참여자만 메시지를 읽거나 보낼 수 있는 규칙은 `chat`
- 게시글 작성자만 수정/삭제할 수 있는 규칙은 `community`

비슷하게 보여도 규칙의 주체와 상태가 다르기 때문에 같은 도메인으로 합치지 않는다.

### 4. 읽기 모델과 파생 뷰의 필요성

이 프로젝트의 최상위 폴더 중 일부는 "원천 비즈니스 도메인"이 아니라 "다른 도메인의 데이터를 조합해 보여주는 컨텍스트"다.

대표적으로:

- `dashboard`
- `timeline`
- `notification`

이들은 보통 다음 성격을 가진다.

- 여러 도메인의 데이터를 모은다
- 원천 데이터를 직접 정의하기보다 가공하거나 투영한다
- 사용자 경험을 위해 읽기 최적화된 결과를 제공한다

즉, 이 프로젝트는 순수한 CRUD 분리만 한 것이 아니라, "핵심 도메인"과 "파생/지원 컨텍스트"를 함께 최상위 수준에서 분리하고 있다.

### 5. 여러 도메인에서 공통으로 쓰는 요소는 `common`으로 분리

모든 공통 요소가 도메인이 되는 것은 아니다.

예를 들어 다음은 특정 업무의 고유 규칙이라기보다 여러 도메인이 공유해야 하는 기반 요소다.

- 공통 응답 포맷
- 보안
- 공통 예외 인터페이스
- 공통 이벤트
- 공용 값 객체

이런 것은 `common`에 두는 것이 맞다.

중요한 점은 `common`이 "아무거나 넣는 곳"이 되면 안 된다는 것이다. `common`은 비즈니스 의미가 약하고 재사용성이 높은 기반 요소만 가져야 한다.

## 현재 프로젝트의 10개 최상위 컨텍스트 해석

현재 구조를 실무적으로 해석하면 다음과 같다.

| 구분 | 이름 | 성격 | 핵심 역할 |
|---|---|---|---|
| Core | `member` | 핵심 도메인 | 회원, 인증, 프로필, 팔로우, 성향 |
| Core | `pet` | 핵심 도메인 | 반려견 정보와 속성 관리 |
| Core | `walk` | 핵심 도메인 | 산책 모집, 신청, 일기, 진행 세션 |
| Core | `chat` | 핵심 도메인 | 채팅방, 메시지, 읽음, 리뷰, 산책 확인 |
| Core | `community` | 핵심 도메인 | 게시글, 댓글, 좋아요, 스토리 표현, 이미지 업로드 |
| Core | `lostpet` | 핵심 도메인 | 실종 신고, 목격 제보, AI 분석, 매칭 |
| Supporting | `notification` | 지원 컨텍스트 | 알림 저장, 조회, 읽음 처리, 실시간 발행 |
| Supporting | `timeline` | 지원 컨텍스트 | 활동 이벤트 누적, 공개 여부 관리 |
| Supporting | `dashboard` | 지원 컨텍스트 | 여러 도메인 데이터를 한 화면용으로 집계 |
| Shared | `common` | 공통 기반 | 보안, 응답, 이벤트, 공용 VO, 공통 예외 |

여기서 중요한 해석은 다음과 같다.

- "10개 모두가 같은 무게의 비즈니스 도메인"은 아니다.
- 실제로는 핵심 도메인, 지원 컨텍스트, 공통 기반이 함께 존재한다.
- 따라서 "도메인이 10개"라고 말하면 대략 맞지만, 설계적으로는 "10개의 최상위 컨텍스트"라고 부르는 편이 더 정확하다.

## 각 컨텍스트를 왜 따로 두는가

### `member`

`member`는 사용자 계정과 정체성의 원천 도메인이다.

이 도메인에서 책임지는 것은 다음과 같다.

- 회원 가입과 로그인
- 인증 토큰
- 프로필
- 팔로우 관계
- 회원 성향/활동 통계

왜 별도 도메인인가?

- 대부분의 다른 기능이 회원을 참조한다
- 하지만 다른 도메인이 회원 규칙 자체를 소유하면 결합이 너무 강해진다
- 그래서 다른 도메인은 `memberId`를 참조하되, 회원의 규칙은 `member`에 남긴다

즉, `member`는 거의 모든 기능이 의존하지만, 그렇다고 모든 기능 안에 녹여 넣으면 안 되는 중심 축이다.

### `pet`

`pet`은 반려견 자체를 관리하는 도메인이다.

여기에는 다음이 포함된다.

- 반려견 등록/수정/삭제
- 품종
- 성격
- 산책 스타일
- 대표 반려견 설정

왜 `member`에 합치지 않는가?

- 회원과 반려견은 1:1이 아니라 1:N 관계다
- 반려견은 자체 속성과 검증 규칙이 있다
- 산책, 실종, 프로필 표시 등 여러 곳에서 참조되므로 독립성이 필요하다

즉, `pet`은 회원 하위 정보처럼 보이지만 실제로는 독립된 관리 단위다.

### `walk`

`walk`는 이 프로젝트의 가장 큰 핵심 도메인 중 하나다.

포함 범위는 다음과 같다.

- 산책 모집글
- 참여 신청
- 모집 상태
- 연결된 반려견
- 산책 일기
- 실시간 산책 세션

왜 하나의 도메인으로 묶는가?

- "산책을 함께 한다"는 하나의 업무 목표를 중심으로 상태가 이어진다
- 모집글과 일기는 API만 보면 별개 기능처럼 보일 수 있지만, 실제로는 같은 산책 경험의 앞단/뒷단이다
- 참여 승인, 정원 관리, 세션 시작/종료 같은 규칙이 하나의 맥락 안에 있다

이 프로젝트에서 `walk`는 단순 게시판이 아니라, 산책이라는 행동 흐름 전체를 담당하는 도메인이다.

### `chat`

`chat`은 대화를 다루는 도메인이다.

포함 범위는 다음과 같다.

- 채팅방 생성
- 참가자 관리
- 메시지 저장
- 메시지 읽음 처리
- 산책 확인
- 채팅 기반 리뷰
- 실시간 전송

왜 `walk`에 붙이지 않는가?

- 산책 모집과 채팅은 연결될 수 있지만 규칙이 다르다
- 채팅은 직접 채팅방, 메시지, 읽음 커서, 나가기 상태 등 자체 상태 모델이 있다
- 실시간 처리와 메시지 조회 방식도 별도 최적화가 필요하다

즉, `chat`은 산책 기능의 부속 UI가 아니라 독립적인 상호작용 도메인이다.

### `community`

`community`는 공개형 소셜 콘텐츠를 다루는 도메인이다.

포함 범위는 다음과 같다.

- 게시글
- 댓글
- 좋아요
- 스토리 형태의 피드
- 커뮤니티 이미지 업로드

여기서 가장 헷갈리는 부분은 `story`다.

현재 구조상 스토리는 `community`에 있지만, 실제 데이터 일부는 `walk`의 산책 일기를 읽어 와서 구성한다. 이것은 경계가 잘못된 것이 아니라, "원천 데이터"와 "표현 방식"을 분리했기 때문이다.

정리하면:

- 산책 일기의 생성/수정/소유는 `walk`
- 그것을 24시간 스토리 묶음으로 보여주는 경험은 `community`

즉, `community`는 콘텐츠의 소비 방식과 상호작용 방식을 책임진다.

### `lostpet`

`lostpet`은 실종 반려견 탐색이라는 별도의 문제 영역을 담당한다.

포함 범위는 다음과 같다.

- 실종 신고
- 목격 제보
- 탐색 세션
- AI 후보 분석
- 후보 승인
- 매치 확정/무효화

왜 별도 도메인인가?

- 일반 게시글이나 산책 모집과는 상태 기계가 완전히 다르다
- 신고 활성 상태, 탐색 세션 만료, 후보 승인 가능 여부 같은 전용 규칙이 존재한다
- AI 연동과 매칭 점수 계산도 이 도메인의 일부다

즉, `lostpet`은 단순 커뮤니티 기능이 아니라 별도의 문제 해결 도메인이다.

### `notification`

`notification`은 알림을 저장하고 전달하는 지원 컨텍스트다.

포함 범위는 다음과 같다.

- 알림 엔티티 저장
- 안 읽은 알림 수 조회
- 읽음 처리
- 실시간 알림 발행

왜 `common`이 아닌가?

- 알림은 단순 유틸리티가 아니다
- 자체 저장 모델과 읽음 상태가 있다
- 사용자에게 보여지는 기능이며, API와 상태를 가진다

왜 핵심 도메인이라기보다 지원 컨텍스트인가?

- 대개 다른 도메인에서 사건이 먼저 발생한다
- 알림은 그 사건을 사용자에게 전달하기 위해 파생된다
- 원천 업무를 직접 만들기보다, 원천 업무의 결과를 전달하는 역할이 강하다

즉, `notification`은 독립 모델은 있지만 주도 도메인이라기보다는 후행 반응형 컨텍스트에 가깝다.

### `timeline`

`timeline`은 활동 기록을 모아 보여주는 지원 컨텍스트다.

포함 범위는 다음과 같다.

- 활동 이벤트 저장
- 회원 타임라인 조회
- 타임라인 공개/비공개 설정

왜 별도 컨텍스트인가?

- 게시글, 산책 일기, 실종 신고 같은 여러 도메인의 결과가 하나의 피드로 모인다
- 타임라인은 원천 데이터를 다시 직접 관리하는 것이 아니라, 이벤트를 정리된 형태로 재구성한다
- 조회 성능과 정렬 기준이 원천 도메인과 다르다

즉, `timeline`은 다중 도메인 이벤트를 모아 만든 읽기 모델이다.

### `dashboard`

`dashboard`는 홈 화면용 집계 컨텍스트다.

포함 범위는 다음과 같다.

- 활동 통계
- 주변 스레드
- 핫스팟
- 내 반려견 요약
- 최근 친구
- 대기 중 리뷰

왜 도메인처럼 분리했는가?

- 홈 화면은 보통 여러 도메인 데이터를 한 번에 가져와야 한다
- 이 조합 로직을 각 도메인 안에 흩뿌리면 화면 요구사항이 핵심 비즈니스 규칙을 오염시킨다
- 그래서 홈 화면 전용 조합 책임을 `dashboard`로 분리한다

즉, `dashboard`는 비즈니스 원천 규칙보다 "사용자 첫 화면 경험"을 위한 조합 책임을 가진다.

### `common`

`common`은 공통 기반 계층이다.

포함 범위는 다음과 같다.

- 공통 응답 모델
- 공통 예외 체계
- 보안
- 공통 이벤트
- 공용 값 객체
- 설정

왜 도메인으로 세지면 애매한가?

- 사용자에게 직접 보이는 업무 기능이 아니다
- 상태 생명주기보다는 여러 도메인이 함께 쓰는 기반 구성요소다

그래서 실무적으로는 `common`을 "도메인"이라 부르기보다 "shared kernel" 또는 "공통 인프라"로 보는 편이 적절하다.

## 헷갈리기 쉬운 경계 정리

### `walk` vs `community`

구분 기준:

- `walk`: 산책이라는 실제 행동 흐름을 책임진다
- `community`: 콘텐츠를 소비하고 상호작용하는 공개 피드를 책임진다

예시:

- 산책 일기 생성은 `walk`
- 산책 일기를 스토리처럼 묶어 보여주는 것은 `community`
- 게시글/댓글/좋아요는 `community`

즉, 원천 행동은 `walk`, 공개형 콘텐츠 경험은 `community`다.

### `chat` vs `notification`

구분 기준:

- `chat`: 대화 자체의 상태를 관리한다
- `notification`: 어떤 사건을 사용자에게 알려준다

예시:

- 메시지 저장/읽음/채팅방 참여는 `chat`
- "새 메시지가 왔습니다"는 `notification`

즉, `chat`이 사건을 만들고, `notification`이 그 사건을 전달한다.

### `timeline` vs `dashboard`

구분 기준:

- `timeline`: 시간순 활동 이력
- `dashboard`: 홈 화면 요약

둘 다 여러 도메인을 모으지만 목적이 다르다.

- `timeline`은 "무슨 일이 있었는가"
- `dashboard`는 "지금 무엇을 보여줘야 하는가"

즉, 둘 다 읽기 컨텍스트지만 조회 목적이 다르므로 분리되어 있다.

### `notification` vs `common`

구분 기준:

- `notification`은 사용자 기능
- `common`은 기반 기술/공용 구성요소

알림은 저장과 읽음 상태를 가지므로 도메인적 성격이 있다. 반면 `common`은 다른 도메인들이 공통으로 기대는 기반이다.

## 이 구조를 설계적으로 어떻게 해석해야 하는가

이 프로젝트는 전형적인 단일 CRUD 분할보다 한 단계 더 나아간 구조를 갖는다.

단순 해석:

- 회원
- 반려견
- 산책
- 채팅
- 커뮤니티
- 실종

여기에 실제 운영에 필요한 파생 컨텍스트가 추가된 형태다.

- 알림
- 타임라인
- 대시보드

그리고 이를 받치는 공통 기반이 있다.

- common

따라서 가장 현실적인 표현은 다음과 같다.

> 이 프로젝트는 "핵심 도메인 6개 + 지원 컨텍스트 3개 + 공통 기반 1개" 구조로 이해하는 것이 가장 정확하다.

## 새 기능이 생길 때 어느 도메인에 넣어야 하는가

새 기능 배치를 판단할 때는 다음 순서로 보면 된다.

### 기존 도메인의 규칙을 확장하는가?

그렇다면 기존 도메인에 넣는 것이 맞다.

예:

- 반려견 예방접종 정보 추가 -> `pet`
- 산책 모집 정원 규칙 추가 -> `walk`
- 채팅 신고 기능 추가 -> 우선 `chat` 검토

### 여러 도메인의 결과를 모아 보여주는가?

그렇다면 지원 컨텍스트를 검토한다.

예:

- 홈 추천 카드 -> `dashboard`
- 활동 피드 -> `timeline`
- 사건 알림 -> `notification`

### 특정 업무의 독립된 상태 기계와 용어를 가지는가?

그렇다면 새 도메인 후보가 된다.

판단 신호는 다음과 같다.

- 자체 엔티티가 필요하다
- 고유한 상태값이 있다
- 전용 에러 코드가 필요하다
- 권한 규칙이 별도다
- 다른 도메인의 하위 기능으로 보기 어렵다

### 여러 곳에서 공통으로 쓰지만 업무 규칙은 약한가?

그렇다면 `common` 후보다.

예:

- 공통 응답 타입
- 공통 이벤트
- 보안 인터셉터
- 공용 값 객체

## 실무적으로 기억하면 좋은 판단 문장

이 프로젝트에서 도메인을 나누는 기준은 다음 문장으로 기억하면 된다.

> "같은 화면에서 쓰이는가"가 아니라 "같은 규칙과 상태 변화를 공유하는가"로 나눈다.

그리고 최상위 폴더를 볼 때는 다음처럼 읽는 것이 가장 정확하다.

- `member`, `pet`, `walk`, `chat`, `community`, `lostpet`은 핵심 비즈니스 도메인
- `notification`, `timeline`, `dashboard`는 파생/지원 컨텍스트
- `common`은 공통 기반

즉, 현재의 10개 분리는 임의로 숫자를 맞춘 결과가 아니라, 업무 책임을 분리하려는 설계 선택의 결과라고 보는 것이 맞다.

## 최종 요약

이 프로젝트의 도메인 분리는 다음 기준으로 이루어진다.

1. 원천 데이터와 비즈니스 규칙의 소유권
2. 상태 변화의 생명주기
3. 권한과 예외 규칙의 독립성
4. 읽기 모델/집계 모델의 필요성
5. 공통 기반 요소의 분리

그래서 현재 구조는 단순한 "10개 기능 폴더"가 아니라, 핵심 도메인과 지원 컨텍스트, 공통 기반을 함께 분리한 설계라고 이해하는 것이 가장 정확하다.
